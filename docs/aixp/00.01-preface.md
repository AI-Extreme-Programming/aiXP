# Preface

The practices described here emerge from a lifetime of software development and early adoption; from an engineering discipline derived from working across variety of projects at a variety of scales in environments that practiced the entire spectrum of "development methodologies." It stems from experience leading production teams, and adapting development practices to the real needs of real projects and developers that don' fit into cookie-cutter versions of development methodologies designed around specific corporate structures and needs.

The practices described here were molded through roughly a year of daily work, pairing with with multiple AI systems (primarily Claude Code, which will be the main example in this document), on real production grade projects;  mobile apps, ai integrations, plugin development, developer tooling, and automation systems. A truly stunning volume completed quickly, in my spare time, while traveling the continent using the cloud, a laptop, an iPad, and more often than you would imagine, just my phone.  None of these methods were invented in advance and then tested. All of it was developed in practice, named after the fact, and cross-checked against existing engineering practices where prior concepts already filled the gaps.

Where a practice here represents something tested repeatedly in production, I'll say so. Where it's adapted by analogy from Lean, SRE, or Agile lineages, I'll name the source. Where it's a working hypothesis that I believe is right but haven't validated beyond my own experience, I'll flag it as speculative.

**What this is not:** a claim that AI makes software engineering easier, or that any particular tool is the answer. The central argument is the opposite: "AI makes the *discipline* of software engineering more important, not less, because the cost of undisciplined code volume is no longer throttled by the speed we type."

**Who is this for?** 

These practices are here to help anyone serious about creating production quality code with AI-native tooling, and anyone interested in keeping AI slop out of their work.  

This book is for experienced engineers, entry level developers, and anyone in tech leadership roles that wants to take advantage of these new technologies without introducing slop and without blowing up their tooling costs.

For the experienced engineer, even those already working with AI-native systems, this provides a coherent, predictable, and efficient methodology - increasing output and reducing costs.  

The entry level software developer has been a particular concern for me.  I have years in leadership and mentorship, and the fear around AI job replacement, speed expectations, and the incredible learning curve required for any quality work today is real.  This system can be used as a learning system - basic programming skills and understanding can be rapidly improved, and that basic understanding can be leveraged into a full-stack force multiplier.

Finally, this book is for working engineers who are already using AI tools and want a coherent model of how to use them without accumulating invisible debt. It assumes you can read code, have shipped software before, and are skeptical of hype. It does not assume you've read Kent Beck, though it will help.

**A note on format:** this started as a brainstorm, became a set of notes, and is now somewhere between a long essay and a short book. The practices are presented as a system - they reinforce each other in ways that only become clear once several are in place simultaneously - but the individual chapters can be read independently if you're looking for something specific.
