## The Problem with Vibe Coding

"Vibe coding" is a term that emerged in early 2025 to describe a particular mode of working with AI coding tools: describe what you want in natural language, accept what the model generates, iterate by feel until it seems to work, ship it. The appeal is obvious. The problem is equally obvious once you've done it long enough.

Vibe coding is not software engineering. This is an operational distinction, not an ethical one. Software engineering requires three minimum capabilities: knowing what the code is supposed to do, verifying that it does so, and understanding what breaks when it changes. Vibe coding provides none of these. It produces output that looks correct and feels like progress, capitalizing on an LLM's strength at generating plausible syntax. But plausible and correct are separate categories, and unverified debt accumulates in the gap between them.

### The failure modes are predictable

They're not random bugs. They're structural:

**Correctness drift.** Generated code passes the immediate test you ran in your head, but fails cases you didn't think of. Without a formal test suite, there's no fast way to know which cases those are until they appear in production.

**Scope creep.** AI tools, when underspecified, don't stay in their lane - they produce the code that *seems* to follow from the prompt, which often includes things you didn't ask for. Without a spec to diff against, there's no way to catch this systematically.

**Context collapse.** Each session starts fresh. The model has no memory of yesterday's architectural decisions, last week's refactor rationale, or the bug you fixed two months ago that this new code just reintroduced. Without maintained context artifacts, this compounds indefinitely.

**Vigilance fatigue.** Reviewing generated code looks like a lighter cognitive load than writing it. It isn't - it's a different cognitive load, and one that degrades faster. Accepting the 40th diff of the day with the same attention as the first is not possible for most people, and the failure mode is invisible: you don't feel yourself rubber-stamping, you just do it.

> [!NOTE] The Genie Eats the Seed Corn
> In [The Genie Eats The Seed Corn](https://tidyfirst.substack.com/p/the-genie-eats-the-seed-corn), Kent Beck uses an agricultural metaphor for unprincipled AI development: *"The genie eats the seed corn."* Seed corn is the grain a farmer saves to plant next season. In software, that seed corn is modularity, clean boundaries, and refactoring. AI coding models have no built-in reward function for "code that is easy to change next month" - they eagerly burn through architectural integrity to satisfy the immediate prompt unless constrained by rigorous engineering discipline.

### Why this matters now

These failure modes existed before AI tools; what changed is the rate at which they compound. A single engineer writing code by hand produces roughly as much change per day as their judgment can evaluate. An engineer pairing with an AI tool can produce an order of magnitude more code per day, but human judgment capacity does not scale with token generation speed. Debt accumulates faster than the feedback loops designed to catch it. The failure is rarely a loud crash; it is an opaque codebase that functions today, resists refactoring tomorrow, and fails in production in ways that defy diagnosis.

The answer is not to abandon AI tools, but to apply the disciplined engineering practices that software systems have always required - updated for an era where generation is instantaneous.
