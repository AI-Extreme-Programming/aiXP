# Chapter 6 - Delivery, Release, and Observability

In classic Extreme Programming (XP), the goal was to ship small releases frequently to shorten the feedback loop between developers and customers. In aiXP, the speed of code generation creates a dangerous illusion: because an AI can generate ten pull requests in an hour, it feels as though the team is shipping ten times faster.

Generating code is not shipping software. A pile of merged diffs on trunk does not create value until it is verified, tagged, deployed, and observed in production.

This chapter details the four disciplines that govern the safe transition from code on disk to verified releases in user hands:

- **Small Releases and Verified Candidates:** Decoupling merge velocity from release exposure.
- **Semantic Versioning and Release Identity:** Maintaining deterministic release identity and automated changelogs.
- **Agent Session Observability and Traceability:** Preserving an audit trail linking commits, prompts, and architectural decisions.
- **Deployment Gating and Blameless Post-Mortems:** Utilizing progressive delivery and error budgets to catch what escapes pre-merge testing.

---

## Small Releases and Verified Candidates

Small Releases in aiXP strictly distinguishes between *generated candidates*, *merged candidates*, and *verified release candidates*.

### The Failure Mode

When generation friction drops to zero, the natural boundary around releases dissolves. Teams begin pushing continuous streams of generated commits directly to end users without explicit gating. When an inevitable regression occurs, diagnosing the cause becomes a nightmare: the failure is buried inside forty concurrent diffs touching twenty different modules.

### The Mechanism

aiXP decouples *merging* from *releasing* through **Feature Flags and Progressive Delivery**:

1. **Merge to Trunk Early:** Code merges frequently to the trunk branch behind dormant feature flags, passing automated unit, integration, and contract tests.
2. **Manufacture the Candidate:** A release candidate is cut deliberately, bundling a small, coherent set of verified changes.
3. **Progressive Rollout:** The feature is toggled on internally for dogfooding first, widened to a small alpha cohort second, and released to general availability only after telemetry confirms stability.

## Semantic Versioning and Release Identity

Release Identity is the discipline of maintaining unambiguous, machine-derivable version numbers that reflect the exact impact of software changes on downstream consumers.

### The Failure Mode

Under high-velocity AI generation, versioning frequently degrades into cargo-culted version bumping or arbitrary timestamps. If an AI modifies an API contract without the team recognizing it as a breaking change, downstream clients break in production with zero warning. Conversely, if versioning is purely manual, developers skip changelog maintenance and tag updates because writing release notes feels like administrative drudgery.

### The Mechanism

In aiXP, release identity is automated by turning commit discipline into a machine-readable contract:

- **Conventional Commits as a Rule:** All commits (whether authored by human or AI) must adhere to the Conventional Commits specification (`feat:`, `fix:`, `refactor:`, `BREAKING CHANGE:`).
- **Automated Version Classification:** Because Context Stewardship maintains the public API boundaries in maintained context files, an AI can inspect diffs against the public contract to classify whether a change is `PATCH`, `MINOR`, or `MAJOR`.
- **Mechanical Changelogs:** Release notes and changelogs are synthesized directly from verified commit history, eliminating manual drafting friction.

### The Concrete Artifact

A prompt constraint enforcing commit identity:

```markdown
Commit the Redis caching changes using Conventional Commits syntax:
- If public interface signatures changed: use `feat!:` or include a `BREAKING CHANGE:` footer.
- If purely internal caching logic: use `feat(auth): add redis fallback to session validation`.
- If fixing a regression: use `fix(auth): prevent null pointer on expired redis key`.
```

## Agent Session Observability and Traceability

Session Observability is the practice of maintaining an immutable, traceable audit trail connecting every production commit back to its originating prompt, spec, and review decision.

### The Failure Mode

Six months after a feature ships, a critical concurrency bug is uncovered in production. The engineers examine git history and find a 400-line diff authored by an AI agent with a generic commit message like *"update payment processing logic."* No one remembers why the AI chose that specific locking strategy, what trade-offs were considered, or which edge cases were evaluated. The team is forced to reverse-engineer the AI's thought process from scratch.

### The Mechanism

In aiXP, traceability is treated as operational telemetry:

- **Prompt and Transcript Logging:** Terminal sessions, prompt briefs, and subagent review summaries are logged and linked to commit metadata or pull request descriptions.
- **Decision Records (ADRs):** Non-trivial architectural choices made during pairing are written directly into repository markdown records before code is merged.
- **Traceable Attribution:** Diffs explicitly document which agent role generated the code and which human Navigator authorized the merge.

## Deployment Gating and Blameless Post-Mortems

Deployment Gating and Blameless Post-Mortems are operational disciplines borrowed from Site Reliability Engineering (SRE) that provide safe landing zones for changes in production.

### The Failure Mode

When an escaped defect hits production in an AI-assisted environment, teams often fall into one of two toxic reactions: either they blame the AI tool (*"Claude broke the build again"*), which leads nowhere because a model cannot learn from blame; or they panic and establish suffocating manual approval bureaucracies that destroy velocity.

### The Mechanism

aiXP relies on two foundational SRE mechanisms:

1. **Error Budgets:** The team establishes an explicit, pre-negotiated tolerance for minor post-release issues. If the error budget is healthy, rapid iteration continues; if the budget is exhausted, new feature generation halts until verification harnesses and test tiers are hardened.
2. **Discipline-Focused Post-Mortems:** When an incident occurs, the team conducts a blameless retrospective focused exclusively on *which layer of the aiXP discipline failed*:
   - Did the specification fail to identify a domain gap?
   - Did Test-Driven Development miss an edge-case assertion?
   - Did the human Navigator suffer vigilance fatigue during Executive Review?
   - Did the CI pipeline lack contract testing for that interface?

By asking which discipline layer failed rather than blaming the tool, the team systematically reinforces their verification factory with every incident.
