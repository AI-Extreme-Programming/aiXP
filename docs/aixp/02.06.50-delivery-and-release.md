# Chapter 6 - Delivery, Release, and Observability

In classic XP, small releases shortened the feedback loop between development and customer reality. In aiXP, generation speed creates a dangerous optical illusion: generating ten pull requests in an afternoon feels like shipping ten times faster.

A pile of merged diffs on trunk delivers zero value until it is verified, tagged, deployed, and observed in production.

Four disciplines govern the transition from code on disk to running software:

- **Small Releases and Verified Candidates:** Decoupling merge frequency from user exposure.
- **Semantic Versioning and Release Identity:** Enforcing machine-derivable release versions and changelogs.
- **Operational Memory and No-Blame Traceability:** Preserving architectural decisions and logging workflow traps (`mistakes.md`, `MEMORY.md`) without tool attribution or blame games.
- **Deployment Gating and Blameless Post-Mortems:** Using error budgets and retrospectives to catch defects that escape pre-merge testing.

---

## Small Releases and Verified Candidates

Small Releases distinguishes among three separate states: *generated candidates*, *merged candidates*, and *verified release candidates*.

### The Failure Mode

When generation friction drops to zero, the natural boundary around releases dissolves. Teams begin pushing continuous streams of generated commits directly to end users without explicit gating. When an inevitable regression occurs, diagnosing root cause is nearly impossible: the failure is buried across dozens of concurrent diffs touching unrelated modules.

### The Mechanism

aiXP decouples *merging* from *releasing* through **Feature Flags and Progressive Delivery**:

1. **Merge to Trunk Early:** Code merges frequently to the trunk branch behind dormant feature flags, passing automated unit, integration, and contract tests.
2. **Manufacture the Candidate:** A release candidate is cut deliberately, bundling a small, coherent set of verified changes.
3. **Progressive Rollout:** The feature is toggled on internally for dogfooding first, widened to a small alpha cohort second, and released to general availability only after telemetry confirms stability.

## Semantic Versioning and Release Identity

Release Identity enforces unambiguous, machine-derivable version numbers that reflect the exact impact of software changes on downstream consumers.

### The Failure Mode

Under high-velocity AI generation, versioning frequently degrades into cargo-culted version bumping or arbitrary timestamps. If an AI modifies an API contract without the team recognizing it as a breaking change, downstream clients break in production with zero warning. Conversely, if versioning is purely manual, developers skip changelog maintenance and tag updates because writing release notes feels like administrative drudgery.

### The Mechanism

In aiXP, release identity is automated by turning commit discipline into a machine-readable contract:

- **Conventional Commits as a Rule:** All commits (whether authored by human or AI) must adhere to the Conventional Commits specification (`feat:`, `fix:`, `refactor:`, `BREAKING CHANGE:`).
- **Automated Version Classification:** Because Context Stewardship maintains the public API boundaries in maintained context files, an AI can inspect diffs against the public contract to classify whether a change is `PATCH`, `MINOR`, or `MAJOR`.
- **Mechanical Changelogs:** Release notes and changelogs are synthesized directly from verified commit history, eliminating manual drafting friction.

### Production Artifact: Conventional Commits and Release-Please Discipline (ScooterGitTemplate)

Across the repository fleet, `CLAUDE.md` enforces strict commit classification so `release-please` never cuts a false minor bump for internal fixes or CI maintenance:

```markdown
- Use Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, etc.):
  - Reserve `feat:` strictly for genuinely new user-facing capabilities.
  - Use `fix:` for bug fixes, lint/type-error cleanups, and DevOps/CI/CD changes on existing projects - even when adding a new workflow or check.
- Release flow (`release-please`):
  1. Conventional commits pushed to `main` cause `release-please` to open or update a release PR bumping the version and `CHANGELOG.md`.
  2. Merging the release PR cuts the GitHub Release and triggers `release-notes-ai.yml`, which generates user-facing notes onto a `pre-release-staging/{tag}` branch for human review before publishing.
```

## Operational Memory and No-Blame Traceability

Operational Traceability preserves the architectural *why* behind every change and captures recurring workflow traps without playing a blame game or cluttering git history with tool credit.

### The Failure Mode

Traceability in AI-assisted development fails in two ways:
1. **Lost Architectural Rationale:** Six months after a feature ships, a subtle bug surfaces in production. Examining git history reveals a 400-line commit with a generic message and zero record of why that seam was chosen or what edge cases were considered.
2. **Performative Tool Attribution and Blame Games:** Teams clutter commit messages and pull requests with `"Generated by Claude"` footers, session URLs, or artificial "agent role" sign-offs, treating git history like a scorecard between humans and machines.

### The Mechanism

In aiXP, traceability captures **engineering intent and institutional learning**, never tool branding:

- **Zero AI or Agent-Role Attribution:** Every repository enforces a hard rule prohibiting AI tool credit, session URLs, or agent-role attribution in commit messages, PR bodies, and code comments (verified via mandatory post-commit and post-PR read-back checks, since hosted agent harnesses inject attribution footers by default). Developers do not sign their work with their compiler or text editor. Moreover, agent roles and titles morph continuously as projects and model capabilities evolve, so recording which "agent role" generated a diff is meaningless noise.
- **No-Blame Mistake Logging (`mistakes.md` and `MEMORY.md`):** We do not play a blame game in aiXP. When an agent or human hits a trap - a misunderstood requirement, a silent API quirk, or a recurring test blind spot - we document it candidly in `notes/dev/mistakes.md` or git-tracked operational memory (`notes/dev/memory/MEMORY.md`). The purpose of logging both agent mistakes and our own mistakes is to adjust our specs, test harnesses, and `CLAUDE.md` guardrails so the failure mode cannot repeat, never to keep score.
- **Specs and ADRs in the Repo:** Non-trivial architectural decisions live in maintained specs and Architecture Decision Records (ADRs) committed alongside the code, ensuring any future human or fresh AI session can read the current truth directly from disk.

## Deployment Gating and Blameless Post-Mortems

Deployment Gating and Blameless Post-Mortems adapt Site Reliability Engineering (SRE) principles to ensure safe landing zones for production changes.

### The Failure Mode

When an escaped defect hits production in an AI-assisted environment, teams often fall into one of two toxic reactions: either they blame the AI tool (*"Claude broke the build again"*), which leads nowhere because a model cannot learn from blame; or they panic and establish suffocating manual approval bureaucracies that destroy velocity.

### The Mechanism

aiXP relies on two foundational SRE mechanisms:

1. **Error Budgets:** The team establishes an explicit, pre-negotiated tolerance for minor post-release issues. If the error budget is healthy, rapid iteration continues; if the budget is exhausted, new feature generation halts until verification harnesses and test tiers are hardened.
2. **Discipline-Focused Post-Mortems:** When an incident occurs, the team conducts a blameless retrospective focused exclusively on *which layer of the aiXP discipline failed*:
   - Did the specification fail to identify a domain gap?
   - Did Test-Driven Development miss an edge-case assertion?
   - Did the human Navigator suffer vigilance fatigue during Executive Review?
   - Did the CI pipeline lack contract testing for that interface?

By asking which discipline layer failed rather than blaming the tool, the team systematically reinforces their verification factory with every incident.
